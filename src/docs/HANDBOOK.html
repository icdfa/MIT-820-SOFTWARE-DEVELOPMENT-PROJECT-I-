Hosting and installation

1. Prepare an isolated installation

Create a new subdomain such as services.your-domain.example, or a new empty subdirectory. Do not extract over the campus portal or over an existing CivicFlow installation. Make a cPanel backup of any existing site before changing its files.

Use an SSL certificate valid for the actual installation address. PHP 8.3 is the tested runtime, with PHP 8.2 as the minimum. Select extensions PDO, PDO MySQL, Mbstring, Fileinfo, OpenSSL, cURL and DOM/XML. DOM enables structured HTML email sanitisation; if absent, the application falls back to escaped plain content. SQLite is optional for local evaluation and requires PDO SQLite.

Recommended initial PHP limits:

upload_max_filesize = 6M
post_max_size = 20M
max_file_uploads = 3
memory_limit = 128M
max_execution_time = 120
expose_php = Off

The application enforces a 5 MB limit per file, three files per upload, 20 files per request and 100 MB per uploading account. These are limits in app/domain.php; adapt them deliberately to your storage budget. No executable uploads are accepted. Files are downloaded as attachments, never served from their storage path.

2. Create the database

In cPanel Database Wizard, create a fresh MySQL/MariaDB database, a unique database user and a strong password. Add the user to that database with ALL PRIVILEGES so the installer can create tables and indexes. The database host is usually localhost; use the value from your host. The installer uses port 3306. If your provider uses a different port, adapt the installer configuration before setup; do not guess credentials.

Do not import database/schema-mysql.sql before the installer. The SQL files are schema references for review and managed migration, while the installer also creates roles, permissions, templates and starter settings.

3. Extract the release

Upload the release ZIP using File Manager. Extract into the document root selected for the domain. Turn on Show Hidden Files and verify the root .htaccess exists. The ZIP contains the application at its root; it is not an SQL backup of the campus portal.

The PHP account must be able to write config/ and storage/ and their children. Use account-owned directories, typically 0755 or stricter permissions compatible with your PHP-FPM setup. Private generated files are 0600. Never use 0777 as a routine fix. If the host runs PHP under a different identity, ask the host for the correct ownership/permissions.

Open the local START_HERE.html to find the setup key. The server blocks this file and config/setup.key from HTTP access.

4. Run setup

Visit the clean route /install. Enter:

  • Exact HTTPS installation base URL, without /install, a trailing query or fragment.
  • Operating organisation and public support email.
  • Fresh database credentials, including cPanel prefixes.
  • Your administrator details and a password of 12–72 bytes containing letters and numbers.
  • Require HTTPS for all live access.
  • Leave demonstration mode off for live use.

For an installation at https://example.org/civicflow, use that full URL as the base. .htaccess uses relative front-controller rewrites and does not require a hard-coded RewriteBase.

After success the installer writes config/local.php and config/installed.lock. It cannot be rerun while installed. A failed setup after schema creation may leave tables: use a new disposable empty database for the retry, or inspect and remove only tables from that failed new installation. Never delete tables from a database in service.

5. Configure the workspace

  1. Confirm the organisation name, support contact and branding.
  2. Configure departments and active officers, including department allocation.
  3. Review service requirements, published fees and calendar-hour targets. Activate each service only when ready. Live starter services are inactive and fees are zero.
  4. Review default roles. Create additional roles where review and approval must be separated.
  5. Enrol the administrator in Account security, save the recovery codes, then require staff MFA if appropriate.
  6. Configure SMTP, SMS and optional AI through Configuration. Credentials are encrypted in database settings using the installation key.
  7. Review public privacy text, FAQs, announcements and template wording against actual operational policies. Update operator-specific privacy/retention text before launch.

6. Schedule work

In cPanel Cron Jobs choose every five minutes and enter the command only in the command box, using the correct absolute path. For example:

/usr/local/bin/php /home/CPANEL_USER/public_html/civicflow/cron/run.php

Equivalent crontab notation:

*/5 * * * * /usr/local/bin/php /home/CPANEL_USER/public_html/civicflow/cron/run.php

Some hosts require a versioned executable such as /opt/cpanel/ea-php83/root/usr/bin/php. Confirm the actual PHP 8.2+ command with the host and enable the same extensions for CLI. Configuration shows the actual application path. The scheduled job processes up to 20 deliveries per run; the manual web control uses up to five to limit request duration. The job is CLI-only. Do not expose it as a secret web URL.

The worker escalates overdue requests, processes up to 20 email/SMS records and records the last run. One invocation can take longer if a provider is slow. A private file lock prevents overlapping delivery workers on the same installation. Retry claiming is conditional in the database as well.

7. Prove the deployed installation

Use your own test accounts and a real recipient you control:

  1. Open /login, /services and /assistant; confirm assets load and links contain no .php.
  2. Request /index.php and /login.php; expect canonical clean-address redirects. Try /config/setup.key, /config/local.php, /storage/ and /app/; expect access denied.
  3. Register a citizen, verify its email, submit a complaint, create a permit with a harmless PDF and confirm a second citizen cannot view either request or its attachments.
  4. Sign in as an officer from the correct department, start review, request information and complete a decision. Confirm an officer from another department cannot read the record.
  5. Confirm internal notes and staff attachments are absent from citizen screens and direct downloads.
  6. Use a reference plus private tracking code, and verify an approved permit record without applicant details.
  7. Confirm cron's last-run time advances and a configured SMTP message is accepted. Check receipt in the destination mailbox. Test SMS and an AI question separately if enabled.
  8. Check desktop, narrow mobile, keyboard navigation, document printing and your current browsers. These visual checks remain hosting acceptance tasks.
  9. Create a backup, restore it to a private staging location and repeat sign-in and document download.

For HTTPS terminated by a reverse proxy, configure a trusted proxy integration at the server/application boundary. The packaged application reads native HTTPS=on; it does not trust client-supplied forwarding headers.

Release cleanup and moving hosts

Keep a copy of the ZIP and setup instructions offline. Delete the ZIP and START_HERE.html from the public hosting directory after setup. The root rules also deny documentation, test, schema and vendor paths; those private directories can remain or documentation/tests can be removed from a live server. Keep all nested protection files.

To move an existing installation, back up and restore the database, config/local.php, config/installed.lock and storage/uploads/ together. Keep the same application key or encrypted integration credentials and MFA secrets cannot be decrypted. Use fresh sessions/rate-limit files on the new host, update the base URL, verify account ownership and cron paths, then test before changing live traffic. This first release does not supply automatic schema upgrades for future releases.

CivicFlow handbook

Citizen and staff guide

Citizen: create an account and sign in

Choose Create account. Enter your name, phone and email, create a password of at least 12 characters including letters and numbers, accept the privacy notice and submit. The portal opens your citizen dashboard immediately.

Check your mailbox for the verification message if email delivery is configured. Open its link and choose Verify email address. You can resend the message from Profile. Verification confirms your email; it does not verify your legal identity.

Use Sign in on later visits. If two-factor login is enabled, enter your authenticator code or an unused recovery code. Forgot password requests a one-hour reset link. If email does not arrive, contact the portal's published support contact.

Citizen: submit a complaint

  1. Open Service directory, search or filter and select a complaint service.
  2. Read the requirements and target time, then choose Start request.
  3. Enter a clear subject, full description, location, state and priority. Explain any urgency in the description.
  4. Attach relevant evidence if available. PDF, JPG and PNG are accepted, at most 5 MB each and three files per upload.
  5. Confirm the information is accurate and choose Submit request.
  6. Keep the reference and private tracking code shown on the request. Request receipt opens a printable record.

Save draft retains the form without sending it to an officer. Required basic details must still be completed. A draft has no service deadline until submitted and stays private to its owner. Use Complete draft to edit and submit it.

The portal is not an emergency response service. Use the appropriate emergency channel for immediate danger.

Citizen: apply for a permit

Choose a permit/licence from Service directory and read its document requirements. Complete the request and attach the supporting documents. A permit with listed document requirements must have at least one attachment before submission; the officer checks whether the evidence is sufficient.

The service authority sets any published fee. This portal does not collect payments or card details. Follow the department's authorised instructions if payment is required.

After approval, open View approval to print or save the application approval record as PDF. The record includes a public verification address. Demonstration installations clearly mark these records as having no legal effect.

Citizen: track and respond

My requests offers subject/reference search, type/status filters and pages of records. Open a request to see its department, assigned officer, target date, documents and status history.

Reply to Needs information with a message and any additional documents. The request returns to the submitted queue. Other citizen-visible messages remain part of the record. Closed requests and drafts do not accept conversation replies.

Withdraw an eligible draft, submitted request or information request using the reason form. A request already in review cannot be withdrawn through this control. A resolved complaint can be reopened with a reason; the department receives a new target. Permits cannot be reopened through the complaint control.

After approval, resolution or rejection you can leave one rating and comment. Reopening a complaint clears the old feedback so the next outcome can be rated.

Track a request also works without signing in, using both the reference and private code. It shows limited status progress for ten minutes and excludes personal details, conversation text and documents. Keep the private code confidential.

Citizen: notifications, assistance and security

Notifications keeps in-app updates even when email/SMS is unavailable. Mark all read when reviewed. Profile lets you update your name and phone, choose routine email/SMS preferences and change your password. Your login email is changed by an authorised account administrator.

The Citizen assistant offers a service guide based on published FAQs. If the operator has configured AI, the screen identifies AI assistance and offers a checkbox to use it. AI questions are sent to the provider with public service facts; avoid entering private documents, identity numbers or passwords. The assistant does not approve applications or inspect private case data. Use the request conversation for individual decisions.

In Account security, add the displayed key to a TOTP authenticator and confirm a current code. Save the eight recovery codes immediately; they are shown once. You can revoke other signed-in device sessions here. A password change signs out other sessions. Keep your device clock accurate for authenticator codes.

Officer: review requests

Your workspace shows submitted requests in your department. Use Assigned to me, Overdue queue and filters to organise work. Department access is broader than assignment; permissions determine the actions available.

Open a request, read its details and download authorised supporting documents. Start with In review and record a clear update. If evidence is missing, choose Needs information and describe exactly what is needed. The citizen's reply returns it to Submitted. Begin review again before recording a final outcome.

A permit can be Approved or Rejected from review. A complaint can be Resolved or Rejected. The form requires an explanation. If another officer updates the record first, reload before saving your decision; version checks prevent overwriting that update.

Use Conversation to send a citizen-visible message. If authorised, select Internal note for staff-only content. Documents attached to an internal note have the same private visibility. Internal note permission is required both to see and to download them.

Department head and administrator

Assignment selects an active, authorised reviewing officer in the request's department. Only roles with cross-department routing permission and organisation scope can change the department. Use Unassigned when no appropriate officer is available.

Reports show status totals, open overdue work, ratings and the share of closed decisions recorded within target. Exports are limited to records in your scope, up to 5,000 matching records per export. Use filters to narrow larger extracts. The auditor role can read submitted records and reports but has no decision or internal-note permission by default.

Administrators create staff accounts, maintain departments/services, manage permissions and configure integrations. Communications officers manage outbox, templates and public content without request access. Refer to OPERATIONS.md for those controls and backup procedures.

Administration and operations

Daily service work

Review the incoming and overdue queues. Confirm unassigned requests have an active, appropriately authorised officer in the correct department. Officers record an explanation with each review, information request and decision. Department heads can export their department's records; administrators manage the whole workspace.

Published targets run in calendar hours. Waiting for information does not pause the clock. Reopening a resolved complaint starts a fresh target and clears prior feedback. Escalation is recorded once per open cycle when cron runs; it is not a substitute for a human response.

Requests and audit records are retained rather than deleted through the application. Deactivate services and suspend accounts to preserve history. This release has no automated retention/deletion engine. The operator must define and implement its retention, erasure and access-request process for the deployment.

Permission governance

Only authorised administrators should manage roles. A role's permissions affect both navigation and direct actions. Default department scope covers every submitted request in the assigned department, rather than only assigned requests. “Assigned to me” is a convenience filter.

Create a custom intake role with department access and requests.review but no requests.decide to separate preparation from decisions. Give the approving role requests.decide. Assignment, routing, reports, exports, documents, communications and configuration have independent permissions. Cross-department routing also requires organisation scope.

Additional roles combine permissions. An account with any department role needs a department. Citizen accounts cannot receive additional staff roles. The primary administrator role is protected. Changes to accounts and roles revoke affected sessions. At least one active primary administrator must remain; an administrator cannot remove its own access through account administration.

Public registration creates citizens only. Staff are created through People and roles. Review all additional permissions before assigning them. users.manage without roles.manage cannot assign privileged/additional roles or modify accounts that already hold them.

Account security and recovery

Every account can enable authenticator-based two-factor login. Setup shows a manual secret and authenticator link. Confirm a current code to enrol, then save eight single-use recovery codes. Enrolment revokes other authenticated sessions. A new sign-in then needs the password plus a current authenticator code or unused recovery code.

Account security lists device sessions and permits revocation of other devices. Password changes and resets revoke old sign-ins. Sessions also expire after 30 minutes of inactivity. An email reset does not disable MFA. A user who loses both the authenticator and all recovery codes needs a controlled operator recovery process; there is deliberately no public MFA bypass.

Require staff MFA only after enrolling the administrator and storing recovery codes. Staff without MFA are directed to Account security before protected workspace access.

Email-verification links expire after 24 hours and are single-use. Password-reset links expire after one hour and are single-use. Resending invalidates earlier verification links. Authentication message bodies are hidden in the outbox interface. Email verification confirms an email address; it is not government identity verification. Registration and basic request access remain available when SMTP is not configured.

Notifications and the outbox

In-app updates are immediate. Routine email and SMS follow account preferences. Authentication messages are sent to the registered email for verification/recovery. The compose screen targets active registered users and respects routine preferences; it is not an unrestricted address mailing tool.

The outbox supports recipient/subject search, channel/state filters, 50-record pages and detailed results. Provider errors shown to staff do not reveal SMTP passwords or API keys. Retry/cancel actions are audited. Existing messages retain their rendered template copy when the template changes.

Delivery is best effort with retries. A provider may accept a message immediately before a process crash, leading to another attempt during recovery. This release does not promise exactly-once delivery or recipient delivery receipts. Stale processing records become retry-eligible after ten minutes.

Provider configuration

SMTP: Set the authorised hostname, port, sender, username and password. Choose STARTTLS (usually 587) or implicit TLS (usually 465), according to the mail provider. Check SPF/DKIM and outbound ports with the host. Do not disable TLS certificate checks. Test with a recipient you control.

SMS: Set the HTTPS API base URL shown in your Termii account, API key, approved sender and generic or DND route. Hosts must belong to termii.com or termii.ai. Nigerian numbers beginning with 0 are normalised to country code 234. Confirm account balance, sender approval, route and applicable consent before enabling. An accepted API response does not prove handset delivery.

AI: Set an available Responses-compatible OpenAI model and API key. AI sends the user's chosen question and public service/FAQ facts, with response storage disabled. It has no tools to change requests, decide applications or retrieve private account data. The interface offers a local service guide when AI is disabled, not selected or unavailable. AI may still produce errors: use department messages for individual decisions or authoritative clarification.

Credentials are stored encrypted under the application key in config/local.php. Blank fields preserve existing credentials; explicit remove checkboxes clear them. Never include that file in public support tickets or source control.

Templates and public content

The template editor supports headings, paragraphs, lists, emphasis, links and tables. Unsafe elements, event handlers and unsupported attributes are stripped server-side. The visual editor synchronises with the HTML source. Plain-text alternatives are stored as well. Preview saved templates before use.

Placeholders: name, title, message, reference, status, service, department, link, app_name, written as {{name}}. Use service_update for workflow updates, welcome for registration and general_notice for general notices. Missing values render blank. Placeholders are escaped in HTML. Automatic updates continue as plain messages if their template is disabled.

Maintain FAQ answers and announcements in Knowledge centre. Review public operator details and privacy text whenever service operations change. The supplied content describes software behaviour and must be adapted to the authority's actual procedures.

Backup and restoration

Use cPanel full-account backup or a protected offsite backup covering these together:

  • MySQL/MariaDB database, or a consistent SQLite backup for evaluation installations.
  • storage/uploads/ and its access-protection file.
  • config/local.php and config/installed.lock.
  • The matching application release and branding assets.

Back up daily at minimum if records change daily, and before changes to the application. Encrypt backups and restrict access. Define retention based on the operator's policy. Session/cache files are replaceable; do not restore old signed-in sessions onto a new host.

For a restoration rehearsal, create a separate private staging domain/database, restore files and records together, update base_url, disable external channels initially, and verify login, MFA, document access, role boundaries and cron. Never test a restoration over the only live copy. A backup without a successful restoration check is not sufficient evidence of recoverability.

Maintenance

Review storage/logs/application.log, outbox failures, disk usage, expired account tokens and inactive device sessions. Set host-managed log rotation and monitor HTTPS, errors, database health and cron. Cache/session cleanup is not automated by the application; use the hosting retention tools and avoid deleting live lock files while jobs run.

Keep PHP and the bundled PHPMailer dependency maintained. Test dependency upgrades against the acceptance suite and a staging SMTP account. Use staged, backed-up deployments; no automatic updater or multi-server storage configuration is supplied.

For capacity growth, use MySQL/MariaDB, monitor real traffic and storage, and benchmark before admitting the intended workload. Multi-node deployment needs shared private uploads, coordinated rate limiting/session storage and deployment-specific locking; the packaged configuration targets one cPanel application instance.

Requirements and acceptance

Project: Smart Government Service Delivery Platform (CivicFlow)
Release: 1.0.2
Prepared for: Group 1, Software Development Project 1
Purpose: Provide a traceable digital route from a citizen's complaint or application to a departmental response.

Problem and proposed outcome

Citizens lose time through queues, repeat visits and unclear service status. Departments also need a reliable record of submissions, documents, ownership and decisions. CivicFlow provides one citizen account, service-specific online forms, permission-controlled staff processing, a visible status history and scheduled notifications. The platform supports e-government service delivery through digital records and connected departmental workflows.

Users and responsibilities

Citizens create their own records and respond to information requests. Service officers process submissions within their department. Department heads oversee departmental workload and reports. Communications officers maintain service guidance and delivery messages. Auditors inspect submitted records and recorded actions. Administrators control accounts, permissions, catalogue and integrations.

Permissions are additive across staff roles and checked on the server for pages, mutations and downloads. Public registration cannot request a staff role. The protected administrator role retains full access. Drafts remain private to their owner before submission.

Business rules

  1. A complaint is resolved; a permit is approved. Both can be rejected after review.
  2. Submitted requests must enter review before a decision. Closed records cannot receive ordinary conversation replies.
  3. A citizen's response to Needs information returns the record to Submitted.
  4. Published deadlines use calendar hours. Waiting for information does not pause the deadline.
  5. An overdue open cycle is escalated once by the scheduled job. Reopening a resolved complaint refreshes its target and permits a new escalation.
  6. No officer may process a request outside their authorised scope. Cross-department routing is separately controlled.
  7. Internal notes and attached staff documents require internal-note permission. Public tracking exposes status only.
  8. Routine external channels follow account preferences. Authentication recovery/verification mail is sent for the account-security action.
  9. “Sent” is provider acceptance, not guaranteed inbox/handset receipt. Delivery stops automatically after five failed attempts.
  10. Live installation starts without demonstration accounts or requests. Starter services require operator activation.

Data scope and integrations

Core entities are departments, services, users, roles, role permissions, additional roles, requests, events, attachments, notifications, outbox, templates, settings, reset/verification tokens, device sessions, recovery codes, audit logs and feedback.

MySQL/MariaDB is the deployment database. SQLite supports local evaluation. SMTP handles email, Termii provides optional SMS, and the OpenAI Responses API provides optional AI. cPanel or a compatible cloud-hosted PHP environment supplies the runtime. Provider credentials and enabled channels are configured by the operator rather than included in source.

Acceptance and exclusions

The attached validation report records what was actually run. The included matrix maps the supplied proposal to functionality; no separate marking rubric was provided, so no grade or complete rubric coverage is claimed.

The release excludes payment processing, national identity checks, government-system synchronisation, cryptographically signed statutory permits, antivirus scanning, automatic records-retention enforcement and recipient delivery webhooks. These require additional authority/provider requirements. Hosting and live-provider acceptance remain deployment activities.

The primary role is stored on users.role; additional roles use user_roles. Template keys on outbox records are references for traceability, while each message stores its rendered body so later template edits do not alter queued text. Reset/verification tokens and recovery codes are stored as hashes. MFA and provider secrets are encrypted under the installation key.

Permission evaluation

A request begins with an active session and account version. The application loads permissions from active primary/additional roles, except the protected administrator role which has the full catalogue. SQL lists use the user's scope and individual record reads enforce it again. Mutations require action permission independently of whether a page or menu item is visible. Downloads also require document permission, request scope and internal-document permission where applicable.

Draft privacy is enforced on individual reads as well as staff lists. Scope precedence is organisation, department, then own. Default citizen permissions can only remain within the allowed public capability set.

Notification processing

flowchart TD
  E["Workflow / account event"] --> I["In-app notice"]
  E --> V["Preference and channel checks"]
  V --> H["Held: configuration required"]
  V --> O["Outbox: pending"]
  O --> C["Worker claim under lock"]
  C --> P["Provider request"]
  P --> S["Accepted: sent"]
  P --> R["Failure: retry with backoff"]
  R --> O
  R --> F["Five failures: stop"]

The job checks disabled channels before delivery and conditionally claims pending/retry rows. Cancellation cannot claim a processing record. Provider acceptance is recorded, but a crash around a provider acknowledgement can still cause a repeated delivery attempt. The system does not claim exactly-once transport.

File and configuration boundary

  • Root .htaccess denies private directories, dot paths, SQL/log/archive artifacts and setup instructions.
  • Each private directory also carries a denial file. Uploaded files have random names, validated MIME types and scoped download routes.
  • Application configuration and install lock are generated locally after setup. There is no bundled live database or account password.
  • SQL reference files are generated from the same schema definitions used by the installer.
  • The application uses a single-instance cPanel topology. Multi-node sessions, shared files, distributed rate limiting and operational monitoring are deployment extensions.
